## 3 变更影响分析（附录 D.4 模板）

**变更编号与描述**

- CR-01：新增"抽签型"报名方式。活动可设为抽签录取，报名期间所有申请进入待抽签队列，报名截止后由管理员触发一次抽签，名额内随机录取、其余置为已拒绝。
- CR-02：新增邮件通知渠道，与站内消息并行，向报名结果追加一封邮件。

**受影响模块**

| 层次 | 具体对象 | 改动类型 |
|---|---|---|
| 枚举 | `PolicyType` | 加值 `LOTTERY` |
| 策略 | `PolicyFactory` | 多注册一个实现 |
| 策略 | `LotteryRegistrationPolicy` | 新增类 |
| 服务 | `RegistrationService.draw_lottery` | 新增方法（`register/approve/reject/cancel` 未改动） |
| 事件 | `EmailNotificationListener` | 新增类 |
| 事件总线 | `build_event_bus` | 多一行订阅 |
| 数据库 | `activity.policy_type` 的 CHECK 约束 | **必须重建表**（SQLite 不支持 ALTER CHECK） |
| 数据库 | `email_outbox` | 新增表 |
| 界面 | 管理台活动列表、活动表单 | 加"抽签"按钮与选项 |

**设计决策**

- 沿用策略模式：抽签只新增一个 `RegistrationPolicy` 实现，报名主流程零修改。
- 沿用观察者模式：邮件只新增一个 `EventListener`，业务代码零修改。
- 抽签结果复用既有状态 `PENDING → APPROVED / REJECTED`，**不新增状态**，避免状态机扩散。
- 唯一绕不过去的是 `policy_type` 的 CHECK 约束：SQLite 无法修改约束，只能"建新表→拷数据→删旧表→改名"。已写成幂等的 `migrate_policy_type()`，随 `init_db` 自动执行。

**新增/回归测试**

- 新增 `tests/test_lottery.py` 共 9 个用例：抽签入池、名额上限、同种子可复现、参与者均收到结果通知、非抽签活动拒绝抽签、无待抽签拒绝、抽签型活动可创建、邮件落库、邮件幂等。
- 原有 C1–C10 全部复测通过，**回归失败数 0**（2 条断言调整见第 2 节，属规格变更）。

**工作量与质量**

- 净工作量约 40 分钟；AI 协作 3 轮（生成抽签实现 / 生成邮件监听器 / 生成迁移脚本）。
- 迁移脚本经真实旧库验证：4 个活动、5 条报名数据在迁移后完整保留。
- 唯一返工：首次把 `activity` 直接 `ALTER TABLE ... RENAME`，会被 SQLite 改写 `registration` 的外键引用；改为"新建 activity_new → 拷贝 → 删除旧表 → 改名"后解决。

**反思结论**

- 策略模式对 CR-01 的收益是**可度量的**：`RegistrationService.register()` 的 diff 为 0 行，新增策略只碰一个文件。
- 观察者对 CR-02 的收益更彻底：`services.py` 完全没改，只在 `build_event_bus` 加了两行订阅。
- 但本次变更暴露了设计的边界：**策略维度可扩展，状态维度不可扩展**。如果 CR 要求的是"候补队列"（需要新增 `WAITLISTED` 状态 + 补位逻辑），策略模式帮不上忙，需要把状态迁移收敛为独立的状态机对象。这说明模式不是万能的，扩展点要落在真正的变化维度上。

**结论**：本次变更的成本集中在一个点——数据库 CHECK 约束。业务逻辑侧的扩展成本接近于零，这正是策略/观察者模式要换来的东西；但代价是 9 个额外类的结构复杂度，对小系统而言属于"可接受但偏重"。
