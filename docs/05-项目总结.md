# 05 项目总结

## 1 做了什么

CampusEvent 是一个校园活动报名与管理系统，覆盖指导书 P2-F01~F08 八个功能模块：管理员发布活动（直接报名 / 管理员审核 / 抽签录取三种报名方式），学生浏览、报名、取消、查看站内消息，管理员审批并查看名额统计。

- 技术栈：Python 3.13 + Flask 3 + SQLite + pytest
- 版本：`baseline-v1`（f7742a1，初始版本，54 个用例）→ `change-v2`（1bfd09c，含 CR-01/CR-02，63 个用例）
- 仓库：https://github.com/king-watermalon/soft2

## 2 设计是怎么定下来的

**第一步，先分职责，不急着写类。** 把需求里的名词和动词拆开：名词（活动、学生、报名、消息）是实体；动词里"校验资格、决定结果、发通知"是三件不同的事，分别落到服务、策略、监听器。这一步决定了后面所有代码的形状。

**第二步，找出真正会变的那一处。** 需求里"报名方式"是显式可变的（初始两种，变更后三种），而"报名流程"是稳定的。所以策略模式包住"决定结果"这一句话，流程本身留在服务里。这里最容易犯的错是把名额检查也塞进策略——它看起来像"规则"，但报名和审批两条路径都要用，而且需要数据库聚合计数，它是**不变量**，不是**变化点**。

**第三步，定事务边界。** 通知失败要不要回滚报名？需求明确"不得让已合法提交的报名无声消失"，所以事件必须在 commit 之后发布，失败只留痕。

## 3 三个关键决策及其代价

| 决策 | 收益 | 代价 |
|---|---|---|
| 报名规则用策略模式 | CR-01 新增抽签时，报名主流程 0 行改动 | 多 4 个类（接口+2 实现+工厂），调用链多一跳 |
| 通知用观察者模式 | 渠道从 1 个到 3 个，业务代码 0 行改动 | 多 4 个类，事件流向需要看 `build_event_bus` 才清楚 |
| 重复报名交给数据库唯一索引 | 并发下正确性有保证，不靠应用层时序 | SQLite 部分索引不好读，排查问题时要记得它的存在 |

`git diff baseline-v1 change-v2 --stat` 的结果是 +318/−4，其中 `services.py` 的 48 行**全部**落在新方法 `draw_lottery` 里，`register/approve/reject/cancel` 一行未改。这是"设计有效"最硬的证据。

## 4 变更暴露的设计边界

这次变更里唯一绕不过去的是数据库：`activity.policy_type` 有 `CHECK (policy_type IN ('DIRECT','REVIEW'))`，加 `LOTTERY` 必须重建表（SQLite 不支持 ALTER CHECK）。写迁移脚本时第一次直接用 `ALTER TABLE activity RENAME`，导致 SQLite 顺手把 `registration` 的外键引用也改了名，数据关系直接断掉；改成"建新表→拷数据→删旧表→改名"才干净。

更大的启示是：**策略维度可扩展，状态维度不可扩展**。如果变更单要求的是候补队列（新增 `WAITLISTED` 状态 + 有人取消时自动补位），策略模式一点忙都帮不上，得把状态迁移收敛成独立的状态机对象。模式的收益只落在它对准的那个变化维度上。

## 5 测试策略

- C1–C10 十个验收用例逐条落到 pytest，一条需求一条测试，不合并、不省略。
- 边界单独建用例：容量为 0/负数、活动已开始、活动已关闭、已取消后重新申请、跨人取消、批准时名额已满、并发唯一索引。
- 通知失败用注入式监听器（`BoomListener` 主动抛异常）验证：报名仍在、`notify_outbox` 记 FAILED、站内消息由另一个监听器正常写入。
- 迁移脚本用真实旧库跑过一遍，核对迁移前后活动数与报名数一致（4 → 4、5 → 5）。

最终 63 个用例全绿。

## 6 问题与反思

**问题一：通知与报名的事务边界一开始写反了。** AI 生成的初版把 `publish` 放在 `commit` 之前，监听器一抛异常，整个报名就被回滚——正好违反需求 B.2-6。改为 commit 后发布，并加 `notify_outbox` 留痕。

**问题二：权限只做了"藏按钮"。** 初版管理台用模板 `{% if me.is_admin %}` 隐藏入口，直接访问 `/admin/` 依然能进。补上服务端 `@admin_required` 装饰器并加测试。**隐藏 ≠ 授权**，这类问题在没有测试的时候几乎发现不了。

**尚存局限**：密码明文比对（演示账号约定，生产应哈希）；SQLite 单写者锁，未做并发压测；邮件只落库未真实投递；抽签用 `random.Random`，未做可审计的种子记录。

## 7 结论

这个项目里，AI 写得快、也写得整齐，但**默认实现经常踩在错误的边界上**——把校验塞进策略、把发布放在提交前、用隐藏代替授权。这些都不是语法错误，是设计判断，只能由人对着需求条款一条条核。真正省时间的不是让 AI 写代码，而是先把类图画清楚，让 AI 在一个不会跑偏的框里填空。
