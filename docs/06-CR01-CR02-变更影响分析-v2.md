## 1. 受影响构件清单

### 1.1 CR-01 年级限定报名

| 构件 | 影响类型 | 说明 |
|---|---|---|
| `student` 表 | 结构：加列 | `grade INTEGER`，可空；NULL = 未登记 |
| `activity` 表 | 结构：加列 | `grade_limit TEXT`，可空；`"2,3"` 形式的白名单 |
| `RegistrationService.register` | 行为：前置拦截 | 被**子类**覆盖，父类源码不动 |
| `activity.policy_type` | **不受影响** | 保持 `DIRECT/REVIEW/LOTTERY`，不新增枚举值 |
| `PolicyFactory` / `RegistrationPolicy` | **不受影响** | 不新增策略类型 |
| `DirectRegistrationPolicy` / `ReviewRegistrationPolicy` | **不受影响** | 行为零变化 |
| `ActivityService` | 不受影响（源码） | 扩展用新方法 `create_limited` / `set_grade_limit` |
| 全部视图与模板 | 不受影响 | 报名结果通过 `flash(result.message)` 呈现，天然容纳新提示 |
| 管理台表单 | 不受影响 | 年级限定走新增的 `/ext/admin` 页面 |

**为什么不动 `policy_type`**：该列有 `CHECK (policy_type IN ('DIRECT','REVIEW','LOTTERY'))`。上一轮加 `LOTTERY` 时被迫写了 `migrate_policy_type()` 重建整张 `activity` 表（`app/db.py:128`），这是那次变更"唯一绕不过去的修改点"。本轮若再加 `GRADE_LIMITED`，必须再重建一次表，且要改 `SCHEMA` 常量本身 —— 直接违反"不修改原有代码"。改用新增列表达年级限定，可以完全避开这条约束。

### 1.2 CR-02 模拟邮件通知

| 构件 | 影响类型 | 说明 |
|---|---|---|
| `EventListener` / `SimpleEventBus` | **不受影响** | 原样复用，异常隔离与 `notify_outbox` 留痕机制直接继承 |

| 编号 | 预计影响 | 实际结果 | 差异说明 |
|---|---|---|---|
| I-1 | 需给 `student` 加 `grade` 列，历史行为 NULL | 一致 | `ALTER TABLE` 加可空列，无需回填 |
| I-2 | 需给 `activity` 加 `grade_limit` 列 | 一致 | 同上 |
| I-3 | 年级不符时必须**不产生任何报名记录** | 一致 | 在 `super().register()` 之前返回失败，用例断言 `registration` 表零行 |

## 3. 两处有意的行为差异

### 3.1 年级判定优先于公共约束

**现象**：在"设置年级限定且名额已满"的活动上，大一学生看到的是"该活动仅限二年级、三年级"，而不是"名额已满"。

**判断依据**：年级限定回答的是"这个活动面向谁"，属于**报名资格**；名额与开始时间回答的是"此刻还能不能报"。资格问题优先级更高，且对用户更可行动——告诉大一学生"名额已满"会误导他以为下次早点来就能报。

**代价**：与原系统的提示优先级不一致。若教师认为应保持原优先级，改法是让子类先镜像父类的前置判定再判年级，代价是判定逻辑在子类重复一遍（父类改动时需同步）。本实现选择不重复。

### 3.2 扩展路径下 `email_outbox` 不再增长

**现象**：走 `app_v2:app` 时，邮件记录只出现在 `email_delivery`，`email_outbox` 保持为空；走 `wsgi:app` 时相反。

**判断依据**：上一轮的 `EmailNotificationListener` 只把邮件塞进 `email_outbox` 排队，没有任何投递器消费它，等于"永远发不出去的队列"。材料要求"由 MockEmailSender 模拟发送，记录…状态与时间"。若保留两份记录，同一个事件会有两条互不一致的邮件流水，CR2-04 关于"不应重复生成多份相同通知"就无法自证。

**代价**：`email_outbox` 在扩展路径下成为历史遗留表。不删除（删表=修改既有结构），在文档中声明其定位为"上一轮未完成的队列"，并保留 `build_event_bus` 与其测试不变。

## 4. 被否决的方案及理由

| 方案 | 做法 | 否决理由 |
|---|---|---|
| A. 新增 `GRADE_LIMITED` 策略类型 | 改 `PolicyType` 枚举 + 改 `SCHEMA` 的 CHECK | ① 必须重建 `activity` 表（上一轮已被迫做过一次）；② `PolicyDecision` 只有 `status`，表达不了"不允许申请"，塞进去要么新增"直接 REJECTED"（污染重复报名判定），要么让 `decide()` 抛异常（破坏策略"无副作用"契约） |
| B. 装饰策略 `GradeGatedPolicy(inner)` | 包装内层策略，在 `decide` 前判年级 | 决策仍需 `Activity` 载体；且 `PolicyFactory` 在 `RegistrationService.__init__` 内默认构造，外部无法注入包装实例，最终仍需猴子补丁 |
| C. 猴子补丁 `helpers.registration_service` | 运行时替换函数 | 全局状态污染，测试间互相干扰，替换点不可见；不采用 |
| D. 装饰器包装服务 | `Extended(delegate)` | 需转发全部方法，父类新增方法时静默失效；无法复用父类内部状态（`self.students` 等） |
| **E. 子类 + 组合根注入（采用）** | 子类覆盖 `register` + `before_request` 预置 `g` | 父类流程零改动、零全局状态，复用请求级缓存这一既有缝隙 |

**关键点**：方案 E 的注入之所以能成立，是因为原代码 `helpers.registration_service()` 写的是 `if "registration_service" not in g`（请求级缓存）。这是原作者留下的**合法扩展缝隙**，不是我们凿的洞。

## 5. "不修改原有代码"的代价，如实列出

| 代价 | 具体表现 | 是否可接受 |
|---|---|---|
| 两套入口并存 | `wsgi:app` 与 `app_v2:app`，部署时必须选对 | 可接受，且带来好处：可随时切回变更前做对照 |
| 管理能力分散 | 年级限定在 `/ext/admin`，原管理台看不到 | 可接受但不够优雅；若要整合必须改 `admin.html` 与 `routes/admin.py` |
| 扩展依赖 `g` 缓存写法 | 若未来有人把 `helpers` 改成每次都 new，注入会失效 | 已用 `smoke_v2.py` 在真实请求链路验证，并在设计文档标注该耦合点 |
| 扩展列由迁移补，不在 `SCHEMA` 里 | 新库初始化后需跑一次 `schema_v2.migrate()`（`install()` 已自动执行） | 可接受；`init_db()` 单独使用时不会带扩展列，属预期 |
| 无法修正原系统的既存缺陷 | 例如 `README` 引用的 `docs/08`、`docs/09` 在 `main` 上不存在 | 不在本轮范围，仅在文档中记录 |

## 6. 回归影响与验证策略

**可能被波及的既有能力**：直接报名、审核报名、抽签、取消、名额统计、站内消息、通知失败留痕、Web 页面。

**验证方式**（三层次）：

1. **单元/用例层**：58 个 pytest 用例（原有 25 + 新增 33），全绿。
2. **服务装配层**：新增用例断言扩展总线的订阅者集合恰为 `{in_app, mock_email, audit}`，防止重复订阅。
3. **HTTP 链路层**：`smoke_v2.py` 用 `test_client` 走真实请求——登录、访问 `/ext/admin`、提交报名、核对页面提示与数据库行数。这一步是唯一能证明"`before_request` 注入在真实视图链路中生效"的证据。

**回归测试与材料条目的映射**见 `docs/08-回归测试表-v2.md`。

## 7. 遗留风险

| 编号 | 风险 | 影响 | 处理 |
|---|---|---|---|
| R-1 | 年级为 NULL 的学生一律不放行 | 老数据学生无法报名年级限定活动 | 有意 fail-closed；提示语引导去补录，管理页可批量设置 |
| R-2 | `grade_limit` 无数据库层约束 | 脏数据（如 `"0,9"`）写入后解析报错 | 写入统一走 `GradeRule.parse()` 校验；已加用例覆盖非法值 |
| R-3 | 并发下邮件可能重复投递 | 极端并发两请求同时通过查重 | 表上有 `UNIQUE(event_id, address)`，第二笔会因唯一约束失败；SQLite 单写者锁进一步降低概率 |
| R-4 | 扩展与 `helpers` 实现的耦合 | 上游改写 `helpers` 会静默失效 | 由 `smoke_v2.py` 覆盖；本文件 §5 已声明 |
| R-5 | 原 `main` 缺失 `conftest.py` | 无回归基线 | 本轮已恢复，25 用例通过 |
